# Compile

Read `../session-plan/references/operations.md`. Resume the exact session. Read approved source bodies, approval qualifications, relevant feedback and reference material, and meaningful unresolved dependencies. Approval without a note accepts the card's recommended action, even if other options remain in the source. Use the recommendation from the approved source version; a user's explicit note or later direction qualifies or overrides it. Apply the same interpretation to legacy approvals using the preserved source and available direction. Multiple options alone are not a reason to ask the user to choose again.

Keep the recommendation's force and scope: “Choose A; also consider B” approves A and leaves B optional, even if both sentences are under Recommendation. “Get A and B” approves the pair; “keep all three as backups” retains all three. For example, approving a card that recommends Wally's among several delis carries Wally's and its relevant links into the plan, and approving a card that recommends LEGO Party! among several games does the same for that game; the other listed delis and games are not thereby selected. An approved component without a choice retains its substantive content. Clarify only genuinely unclear or contradictory recommended actions or user direction. Deliberately retained alternatives or backups belong in the plan.

The thinking happened on the board; this is where it becomes something a person can pick up and use. Write the plan as a well-put-together, presentable document for a human reader — not an assembly of cards. Open with an executive summary: a few sentences on what the plan achieves, the decisions that define it, and what happens first. Then present the actionable detail — relevant links, constraints, logistics and dependencies — in whatever arrangement reads best for this plan, under headings that coverage can point to, with supporting rationale and clearly separated open notes where useful. Do not reproduce Context/Content/Options/Recommendation mechanically, print discarded research, or imply that approval means a purchase or booking occurred. Keep approved detail and requested contingencies substantial enough to act on.

Review your draft against each approval: does it carry forward the accepted recommended action and honor any user qualification, preserve important constraints and links, exclude discarded options, and distinguish unresolved matters? Group related items freely. Supply coverage using each current `approvalBasis` and exact headings in your document, as described in operations. The server checks current evidence and coverage; it cannot verify semantic faithfulness. If the session changes, reread and reconcile rather than retrying with a fresh revision alone.

Before publishing, have the draft checked by someone who did not write it. Delegate the check to a subagent. Give it the draft file's path, the exact session name, the helper's location and the session store (`--runs`) if it isn't the default, and have it read the approved cards, their approval notes and relevant feedback with `resume`. Tell it that staging a card accepts the card's recommended action unless the user's note says otherwise, and that optional additions stay optional, so a recommendation staged without a note is settled, not unresolved. Pass along any direction the user gave in chat that qualifies an approval, since the checker cannot see the conversation. It compares those against the draft and reports, card by card, anything dropped, distorted, added beyond what was approved, or presented as settled when it is unresolved — naming the card and the passage. It changes nothing: it never writes cards, drafts or outputs, and never runs `compile`. You assess its findings, revise the draft where they hold, and then compile. If the host cannot run subagents, do this check yourself as described above. When you return the plan, tell the user whether an independent check ran and what it changed.

Use `compile` to publish the composed document and its server-generated source record in a new output bundle. Do not change source cards or statuses. `export-sources` is the separate verbatim-record operation, not the finished-plan default. Existing outputs remain.

Return a clearly labeled clickable link to the exact output. If the user designated a parent workspace for the planning work, record a durable pointer there to the session and output — at the location the intake records or, if it records none, where that workspace's conventions put it — preserving existing text. The returned `parentWorkspace` is a location hint, not authority to overwrite files. Use one canonical output; copy it only when requested. Ask only if a requested parent handoff has an unclear destination. With no parent designated, the canonical output and its clickable link are sufficient. The session remains resumable.

After a successful compile, proactively ask whether the user is finished with the board and wants the local server stopped. Explain that saved work remains available for later. If shutdown is already explicitly requested, act on that direction without asking again. Follow the operations reference's lifecycle guidance: account for other planning surfaces and have the user save unfinished input when relevant; the agent cannot see every browser draft or open tab. A shared-server refusal does not authorize an automatic retry with `--all`. Report the actual shutdown result. Do not stop merely because compiling or an agent response finished.
